# Webots 3D validation report

**Read this first.** Webots was **not available** in the authoring environment (no `webots`, no Webots `controller` Python module, no network, no Windows). Therefore:

* **No scenario was executed in Webots. No Webots log, trajectory or metric exists in this release.**
* Everything labelled *stand-in* below was run through the real adapter + the real ResilientSync engine, but with a **Python differential-drive stand-in plant, not Webots physics**. It validates the pipeline (frames, command conversion, fault injection, logging, analysis), **not** the Webots world, the PROTO, the physical behaviour, or the Webots API calls.
* All Webots-side files (`.wbt`, `.proto`, two controllers, launcher) were written from knowledge of the Webots API and are **unverified until you run them** (section 7).

## 3. Architecture and what the controller can see

```
Webots: robots (RSDiffDrive) --poses--> rs_coordinator (Supervisor) --wheel speeds--> rs_wheel_driver (x N)
                                            |  WebotsAdapter -> ORIGINAL engine (controllers, supervisor, Network+faults)
                                            |  logs steps / comm events / deliveries / transitions
```
The coordinator runs **one** engine instance for all robots (the engine is a global-state simulator). Wheel commands travel over a Webots Emitter/Receiver pair on channel 1 (simulation plumbing, ~1 basic step latency, **not faulted**). The radio link under test is the engine's `Network`, so injected faults change what the follower controllers receive, not only the plots.

| Quantity | Source in the closed loop | Realistic? |
|---|---|---|
| Leader pose at followers | **only** via the faulted network (dead-reckoned from the last delivered packet) | yes |
| Own pose and velocity | ground truth from Webots (`getPosition/getOrientation/getVelocity`) + the engine's own Gaussian error noise | **idealised**: no odometry/GPS/IMU model |
| Neighbour poses (coupling, avoidance, yield) | ground truth, global | **idealised** (engine limitation 5 in HANDOFF) |
| Leader command | open-loop trajectory (engine) | n/a |
| Evaluation metrics (`formation_rms`, `min_sep`, `true_slot_err_*`) | ground truth | evaluation only |

Frame: Webots world is set to **ENU** (`coordinateSystem "ENU"`), RS frame = ENU, identity map by default (`FrameMap` supports offset/rotation; tested). Heading = `atan2(R[3], R[0])` of `getOrientation()`; `v` = world velocity projected on the heading; `omega` = `wz`. Reference point = axle midpoint (PROTO `centerOfMass 0 0 0`, so `getVelocity()` is the origin velocity). Time: `basicTimeStep` 10 ms, control period 50 ms = engine dt; `max_time_skew_s` in `meta.json` reports any drift between the Webots clock and the engine tick.

Known differences from the Python simulator (expected, not yet measured in Webots): the engine plant is RK4 with a tau = 0.12 s velocity lag and no wheels; Webots has wheel/ground contact, mass, motor torque limits and a one-step Emitter/Receiver hop. The adapter measures poses *before* commanding (one-tick ordering difference from the native step, where the leader moves before the broadcast). No numerical equivalence is claimed.

Reproduce: `python scripts/run_staged_standin.py eval` then `python scripts/analyze_runs.py --runs results/standin/eval --out results/standin_report/eval --reference --plot-seed 42`. Per-run table: `results/standin_report/eval/per_run_metrics.csv`.

**Supervisor states actually reached** (supervisor arm, all 10 seeds pooled; `results/standin_report/eval/supervisor_states_reached.txt`): all four states (NORMAL, DEGRADED, HOLD, RECOVERING) in `blackout_gentle`, `blackout_3s` and `burst_loss`. **HOLD and RECOVERING were never reached** in `nominal_gentle`, `random_loss_30` and `latency_jitter`: the loss/latency never made message age long enough (max age 1.05 s random loss, 1.25 s latency vs 3.3 s blackout). HOLD is age-driven in this implementation (HANDOFF section 4), so this is expected, not a defect. DEGRADED appears even in `nominal_gentle` because the default channel itself is lossy (the supervisor thresholds were calibrated around that).

### What the logs demonstrate (stand-in, seed 42/100 verified directly in the CSVs)
* **Fault injection reaches the controller.** In `blackout_gentle`, all 240/240 pose messages sent in [5, 8) s are `LOST`; zero accepted deliveries in (5.5, 8) s; deliveries resume at t = 8.05 s; follower message age ramps to ~3.1 s and collapses at restoration (`tests/test_webots_faults.py`, plus `deliveries.csv` / `comm_events.csv`).
* **Supervisor transitions** NORMAL -> DEGRADED -> HOLD -> RECOVERING -> NORMAL occur in the blackout; time until all followers are back in NORMAL after the blackout ends ≈ 2.0 s (10 seeds, 1.95-2.10 s).
* **No collisions** in any of the 240 evaluation runs (min centre distance 1.07 m vs 0.38 m threshold). Note the Webots robot body is 0.40 x 0.26 m, so the 0.38 m centre-distance threshold is a Python-simulator criterion and is only a proxy for body overlap.
* **No wheel-speed saturation** (0 samples): the engine's limits (1.25 m/s, 2.4 rad/s) fit inside the 20 rad/s wheel limit.

### Observations to treat carefully
1. **Recovery criterion** (the existing `compute_recovery_metrics`: absolute tolerance 0.5 m, relative 1.25 x pre-fault baseline over 1 s, sustained 0.5 s): for `blackout_gentle` the error peaks at ~0.5 m, essentially at the threshold, so the declared "recovery time" is 0.0-0.3 s and nearly uninformative; time-to-all-NORMAL (~2 s) is the more meaningful number. For the default-path scenarios the formation error is ~1.5 m even without faults (HANDOFF finding 4: the default leader path is infeasible for outer slots), so **0/10 runs "recover"** by the declared criterion. This reproduces the Python simulator; it is not a Webots effect.
2. **Controller ranking is not in favour of the supervisor on RMSE.** Under `blackout_gentle`, PIDR 0.131 and Advanced 0.124 beat Adaptive+Supervisor 0.171 and Adaptive legacy 0.211; the same ordering holds in the native Python simulator on the same seeds (supervisor − PIDR: +0.026 m native, +0.039 m stand-in). This agrees with HANDOFF section 5 (PIDR lowest RMSE). No claim of superiority of the supervisor on tracking error is supported by these runs.
3. **Stand-in vs native:** with the *same* plant model (engine RK4) the adapter reproduces native RMSE closely (`nominal_gentle` supervisor: 0.059 vs 0.058; `blackout_gentle` supervisor: 0.168 vs 0.144, seeds 100-102), the residual being the measure-then-command ordering. With the wheel-level stand-in plant RMSE is higher by ~0.005-0.05 m. Differences are small but real; not "equivalent".
4. **Command chatter (risk for Webots).** All four controllers change `v` by ~0.55-0.60 m/s and omega by ~1.8 rad/s between consecutive 50 ms ticks (seed 42, `blackout_gentle`): the engine feeds measurement noise straight into commands and its tau = 0.12 s lag smooths it. A real 8 kg robot with torque-limited motors will filter differently. It is **unmeasured in Webots** and the first thing to inspect in a Webots run (wheel speed traces, motor torque warnings, jitter). I did not tune it.

## 7. Unverified / unresolved (requires Webots)

1. `.wbt` / `.proto` have never been opened in Webots: syntax errors, `R2023b` header vs your installed release (Webots offers to upgrade older worlds), physics stability (casters via `contactMaterial "rs_caster"` friction 0, 8 kg body, wheel mass) and the camera viewpoint (its orientation is checked mathematically, not visually) are all unverified.
2. Webots API usage in both controllers is from knowledge, not execution: `Receiver.getBytes()` (falls back to `getData()`), `resetPhysics()`, `getVelocity()` semantics, `simulationQuit()`, `Supervisor.getFromDef`, `getVersion`/`getWorldPath` (guarded by `hasattr`).
3. Placement: the coordinator teleports robots to the engine's seeded initial poses, then advances **one control period with zero commands** so `getPosition()` reflects the teleport; `plant.time()` is measured from there. If this misbehaves it shows up as non-zero `max_time_skew_s` or an initial pose jump in `steps.csv`.
4. Webots CLI flags (`--mode=fast --batch --minimize --stdout --stderr`) and the Windows install path discovery in `scripts/run_webots_trials.py` are from memory.
5. Python in Webots must have `numpy` and `scipy`; set it via Webots Preferences or `controllers/rs_coordinator/runtime.ini` (see `runtime.ini.example`).
6. No Webots-vs-Python-simulator comparison exists yet; the only matched comparisons are native-vs-stand-in (section 5).
7. The dashboard fix (`ROLLING_WINDOW_UI_FIX.md`) and estimator audit (`ROLLING_WINDOW_AUDIT.md`) were not part of this work and were not re-verified.
